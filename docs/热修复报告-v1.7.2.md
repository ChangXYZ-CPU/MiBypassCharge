## 0. 结论速览

本轮针对真机反馈的 4 个问题做热修复，并顺带查出一个隐藏的多实例 bug。核心结论：

1. **"关总开关不省电"** —— 旧版 `ENABLED=0` 只是让守护低频空转，daemon / supervise / watch 三个进程一个没停。现改为**彻底 kill 全链路**，零常驻零唤醒。
2. **"手动模式回不到自动"** —— 旧 `resume` 把 MODE 写成 `force_off`（手动充电），只有充满 100% 才回 auto，实际卡死。现**弃用 force_off**，按钮改为"立即旁路 ↔ 恢复自动"两态，旧配置自动迁移。
3. **"点击响应慢 / 开关颜色不同步"** —— 根因不是网络延迟，而是 **`background` 走主线程 paint，被 KSU 同步 `exec` 冻结**（详见 §3）。改用 `opacity` 合成层后两者同步。
4. **"watch 开关提示误闪"** —— 异步启动期间 status 未反映，被误判成"启动失败"。现加启动宽限期。
5. **隐藏 bug：watch 堆 4 个实例** —— 子 shell 继承 EXIT trap 删父锁 + `start_all` 主动删锁，两个原因叠加。已修，现在严格保持 1 主 + 1 管道子。

## 2. "关总开关彻底停进程"实现要点

旧逻辑的问题：`ENABLED=0` 后 daemon 主循环仍在跑（每 60 秒醒一次）、supervise 仍在 wait、watch 仍在跑 logcat。三个进程一个没少，只是不做决策。

新逻辑（`bg-ctl.sh`）：

```
set ENABLED 0
  ├─ smart_clear          先松开停充位（否则插电不充，v1.6.1 踩过）
  ├─ stop_all
  │    ├─ kill supervise  必须最先，否则它 3 秒后把 daemon 拉活
  │    ├─ kill daemon
  │    ├─ watch_stop      轮询 0.2s 检测，退出即返回
  │    └─ 清 pid 文件
  └─ 完成
```

开机入口 `service.sh` 改走 `bg-ctl boot`：`ENABLED=0` 时只恢复充电、不启动任何进程，判断逻辑集中在一处。

**真机验证**：关后 `daemon/supervise/watch` 全为 0，UI 显示"已停止（省电）"；开后可完整恢复 1/1/2。

## 3. 开关视觉不同步的根因（本轮最关键发现）

### 现象
点击开关后：**滑块立刻滑到另一侧，但背景仍是蓝色**；等到系统 toast 弹出（命令返回）背景才变黑。

### 根因
开关的两个视觉属性走了**不同的渲染管线**：

| 属性 | 渲染路径 | 受主线程阻塞影响 |
|---|---|---|
| 滑块位移 `transform` | GPU 合成层 | ❌ 不受影响，立刻动 |
| 背景色 `background` | 主线程 paint | ✅ 被冻结 |

KSU 的 `exec` 在部分版本会**同步阻塞 JS 主线程**。阻塞期间主线程的 paint 发不出去，所以背景卡在蓝色；而 transform 在独立合成层，不受影响先动了。命令跑完、主线程解锁（正是 toast 弹出那一刻），背景才补上变黑。

**这也说明早先加的 `nextFrame`（让出一帧再发命令）是无效的**——让出一帧后 exec 照样阻塞，主线程一冻，paint 仍然发不出去。

### 修复
把蓝色背景从"直接改 `background`"改成"独立的 `::before` 覆盖层 + `opacity` 过渡"：

```css
.track{ background:#33333c; overflow:hidden; will-change:opacity; }
.track::before{ background:var(--blue); opacity:0; transition:opacity .18s; }
.switch input:checked + .track::before{ opacity:1 }
.switch input:checked + .track::after{ transform:translateX(20px) }
```

`opacity` 与 `transform` 同属合成层属性，不受主线程阻塞影响，两者即可严格同步。

**真机验证**：用户确认"正常了"——点下去滑块与背景同时变化，不再等 toast。

## 4. watch 多实例 bug（排查中额外发现）

### 现象
`pgrep -f bg-watch` 显示 **4 个** bg-watch 进程（应为 1 主 + 1 管道子 shell = 2）。

### 根因（两处叠加）
1. `bg-watch.sh` 用 `trap 'rm -rf $LOCK' EXIT` 释放锁。但 `logcat | while read` 会 fork 一个**子 shell**，子 shell 继承了这个 EXIT trap——它一退出就删掉**父进程仍持有**的锁，导致下一个实例能起来。
2. `start_all()` 里主动 `rm -rf .watch.lock`，使 `watch_start` 的去重判断失效，每次 boot 都多起一个。

### 修复
```sh
# 1. 锁释放加 pid 校验：只有持锁者本人退出才删
release_lock() { [ "$(cat "$LOCK/pid")" = "$$" ] && rm -rf "$LOCK"; }

# 2. watch_start 改用进程表去重（不依赖锁文件）
watch_start() { [ -n "$(watch_pids)" ] && return 0; setsid sh bg-watch.sh & }

# 3. start_all 不再删锁
```

**真机验证**：清→0、开→2、反复开关 3 轮仍 2、重复 boot 仍 2，不再堆积。

## 8. 遗留说明

1. **`smart_clear` 的 3 秒等待是硬件必需**（驱动要求 `0x2` → 等 3~6 秒 → `0`，否则可能解不掉停充位）。所以"关总开关"的 toast 仍需约 3 秒才弹，这是如实反映驱动收尾，非前端卡顿。
2. **界面元素测试依赖人工操作**，脚本只能校验 DOM 结构与关键代码存在性；视觉同步已由用户实机确认。
3. 修复仅在 K70（SM8550）真机验证，其它机型未测。
